# LLVM 19 与 macOS LLVM 22 归档裁剪设计及实施计划

> 2026-09-16 交接状态：本轮只完成归档盘点、macOS LLVM 19 裁剪候选及测试探针，未更改正式归档或目录。用户最新要求仅在本地处理并验证 `just build-secure-env` 使用 LLVM 22；若 macOS `secure_env` 成功移植，应取消 macOS LLVM 19，而非继续裁剪它。以下四包裁剪顺序因此暂停，须由接手者先按最新要求重新判定范围。体积测试需显式设置 `CDH_LLVM19_ENFORCE_SIZE=1` 才运行；对现有归档预期报红。

## 目标与边界

减少 `darwin-arm64`、`linux-arm64`、`linux-amd64` 的 LLVM 19.1.7，以及 `darwin-arm64` 的 LLVM 22.1.8 首次同步和安装量。每项独立验证、提交并推送 `main`，随后立即同步主仓 gitlink。本计划对应工具链仓 issue #4，不改变工具链版本、宿主架构或项目编译目标，不修改 Linux LLVM 22 归档。

当前归档基线：LLVM 19 的 macOS arm64 与 Linux arm64 各约 1.3 GiB、15 卷，Linux amd64 约 1.5 GiB、18 卷；macOS LLVM 22 约 1.4 GiB、16 卷。Linux LLVM 22 已是单卷，不能把它的目录清单直接用于 macOS。macOS `secure_env` 固定 LLVM 19.1.7，但现有 Bazel 规则仍下载官方包；Linux `secure_env` 实际选择 LLVM 22.1.2。缩减预编包本身不能冒称已消除 Bazel 下载。

## 保留原则

- 按主仓实际调用路径列出原生 Clang、Clang++、同版本 LLD、`llvm-ar`、读取/剥离/归档等宿主辅助工具。保留 Clang resource 目录、编译链接所需库及其传递依赖；macOS LLVM 22 还要保留实际需要的 `libclang` 动态库及加载依赖。
- 保留各归档上游许可证和已有第三方通知；`catalog` 中登记新归档和每卷的实际字节数、SHA-256，任何卷不超过 90 MiB。普通文件独立 inode 且 `st_nlink == 1`，不生成或恢复硬链接；符号链接必须留在包内。
- 不通过系统、Homebrew、APT 或其它架构的工具静默补足裁掉的内容。原始归档作为只读输入保留在 Git 历史；新归档在仓内暂存、验证，再替换该项当前分卷，不碰其它工具链与用户工作区。

## 实施顺序与可观察条件

1. 盘点四份包的实际文件、执行文件依赖和主仓消费者，记下原始压缩字节、分卷数与候选清单。检查当前宿主测试和安装能力，记录无法原生运行的宿主验证路径。
2. 先在对应宿主 Go 模块加入制品行为测试：经正式安装后，身份、架构、权限、文件身份、C/C++ 编译链接、归档/读取等所需命令必须通过；压缩总量与分卷数须较基线至少减半。每项生产归档更改前运行并记录预期红灯，不用源码文本断言。
3. 依次裁剪并发布 macOS LLVM 19、macOS LLVM 22、Linux arm64 LLVM 19、Linux amd64 LLVM 19。每项只改其归档、类型化目录、聚焦测试、许可证记录和必要文档，运行 Go 测试、`go vet`、安装器 `check`、原生编译链接与受影响的主仓入口；版本文件在该项其余编辑和审查之后最后修改并立即提交推送。
4. 每次子仓 push 后，下一写操作仅同步主仓 gitlink，验证主仓从空对象缓存可获取登记对象，再按主仓版本和提交规则独立 push。跨宿主测试不能用 macOS 执行 Linux ELF 冒充原生验证；Linux amd64 可使用同架构 Docker，Linux arm64 使用同架构 Docker 或登记验收机。
5. 四项全部通过后复核 `just toolchain-init`、`toolchain-check`、M1 Max `just build-qemu-cdh` 的正式命令与实际结果，向 issue #4 写入压缩前后大小、安装和编译证据，再关闭。任何构建失败只修正该失败所属项，不放宽工具链身份要求。

## 回退

候选归档或原生构建失败时不推送该项；保留上一个已验证分卷和目录。已推送的缺陷通过新的前向小提交修复，不重写 `main` 或移动 tag。M1 Max 现有安装和源码不由本计划直接覆盖，待它自身安装结束后使用 Git 同步。
